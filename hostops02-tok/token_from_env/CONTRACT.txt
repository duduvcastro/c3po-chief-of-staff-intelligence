3. SPECIFICATION

3.1 What it does. One run: everything is looked at; one exclusive create of /etc/c3po-bar/token relative to the held
descriptor of the configuration directory (O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0600 under umask 0077); the value
of the environment file and one newline written; fsync of the file; its metadata by descriptor; fsync of the directory;
the readback (op.py, place_token). DESIGN.md sections 1, 5 and 6.

3.2 Days. The class WRITE_WEEKEND of the core (the dispatcher's literal: 2026-10-02, 03, 04), narrowed by the source to
2026-10-03 and 2026-10-04 UTC (TOKEN_DAYS, validate_plan). Gate at most 900 s. The binding puts the window before the
Sunday read L5 (section 4).

3.3 Authentication. The family's, unchanged: four pins, canonical documents, exact key sets, the hash chain, owner, host
binding, transport binding, claim root, date and windows, evidence naming GO_READONLY_HOSTOPS_PRECHECK_01 and
GO_WRITE_SUPERVISOR_READER_PROVISION_01, scope, effects recomputed and compared, success criterion
TOKEN_PLACED_METADATA_VERIFIED.

3.4 Plan refusals (from the bytes, locally in the dispatcher before any claim; validate_plan), in this order:
CHAIN_ROW_INVALID / CHAIN_ROW_UNSAFE / PARENT_SETGID (the signed rows of /etc/c3po-bar), CONFIG_DIRECTORY_NOT_ROOT_0700,
DEPLOY_DIRECTORY_INVALID (not a clean absolute path, "/", or containing or inside /etc/c3po-bar), EVIDENCE_BOOT_UNBOUND,

3.6 The parsing rules (ENV_RULES, token_definitions, value_boundary, token_content; DESIGN.md section 4 has the reasons):
  a. no carriage return and no NUL byte anywhere in the file;
  b. every line blank (spaces, tabs), a comment ("#" after spaces and tabs), or a statement: [spaces/tabs]
     ["export" spaces/tabs] NAME [spaces/tabs] "=" or ":" [spaces/tabs] VALUE, NAME of A-Z a-z 0-9 _ . - [ ]; a name
     without "=" or ":" is refused (revision 2);
  c. a VALUE of another name that begins with a quote closes on the same line at the next quote of its kind, holds no
     two consecutive backslashes and no backslash just before that quote (revision 2: other backslashes are accepted),
     and is followed only by spaces, tabs and an optional comment;
  d. an unquoted VALUE of another name ends at the end of its line and does not begin with a vertical tab, a form feed
     or a byte above 127;
  e. a statement whose NAME is MASSIVE_API_TOKEN or C3PO_MASSIVE_API_TOKEN without regard to case is a definition,
     and must be exactly NAME=VALUE (capitals, column 0, no export, no space around "="); its VALUE is judged by g alone
     (revision 2), not by c and d;
  f. no line but a definition and the comments holds massive_api_token in any case, the Kelvin sign read as "k": not
     inside or around another name, not in a value of another name (revision 2);
  g. at least one definition; all definitions byte-equal;
  h. the VALUE matches [A-Za-z0-9._~+/=-]{16,512} to the end of its line;
  i. the token file holds the VALUE and one newline (17 to 513 bytes).

3.7 After the creation nothing refuses unless nothing changed. Exit 0 requires: the create, every write, fsync of the
file, the metadata (regular, uid 0, gid 0, 0600, one link, the size written, the device of the directory), fsync of the
directory, the directory proved again from "/", the readback (same inode, uid 0, gid 0, 0600, one link, size within
1-4096, bytes equal). Otherwise PARTIAL (exit 2), with token_file.state:
  WITHDRAWN               the file this run created was removed (the name showed its inode with one link), directory fsynced
  WITHDRAWN_NOT_DURABLE   removed; the fsync of the directory after the removal failed
  LEFT_UNVERIFIED         the file may hold anything: withdrawal not allowed (GO expired, clock reversed, directory
                          replaced), not this run's file at the name (another inode or a second link), or the removal
                          failed (withdrawal_code); with fsync_file false it may be EMPTY or partial
  CREATE_UNCERTAIN        the exclusive create did not return (objects_left_by_this_run null)
An exception that escapes (the death of the process) is PARTIAL_STATE_UNKNOWN_TOKEN_FILE_MAY_EXIST.

3.8 What never happens. No process; no environment of a process read (os.environ is not named); no docker, systemctl or
shell; no network; no overwrite, rename, chmod, chown, truncate; no removal of anything but the token file this run
created (3.7: a declared exception to rule 4 of the core, signed in the scope as exceptions_to_the_core); no second
attempt; no activation; no core dump of the process once anything is opened (3.10).

3.9 Receipt (DESIGN.md section 7). Listed codes, booleans and identity rows only: the signed rows of /etc/c3po-bar, the
device and inode of the token file created; never the value, a digest of it, its length or a line count, never a byte
or a row of the deploy tree or of the environment file. environment_file.not_readable_by_group_or_other says whether
the file was readable by group or other as found (it never refuses). process.dumpable_disabled (revision 3) says
whether the process was made non-dumpable (true) or could not be (false, and the run refused with
PROCESS_DUMPABLE_NOT_DISABLED). The receipt of a run does not depend on the token (tested: byte-identical receipts for
two tokens of different lengths and first bytes).

3.10 The process made non-dumpable (revision 3; the scope signs it as "process", the effects as "process"). The first
step of the run, before the deploy directory, the environment file or anything else is opened (perform: the first call
of the precheck), is the core's NativeRead.not_dumpable(): dumps_disabled() loads the C library of the interpreter
(ctypes.CDLL(None, use_errno=True), inside the function, never handed out), calls prctl(PR_SET_DUMPABLE=4, 0), which
must return 0, then prctl(PR_GET_DUMPABLE=3), which must answer 0. Anything else (the library or its prctl missing, a
call returning anything else or raising) is Refused('PROCESS_DUMPABLE_NOT_DISABLED'): the run refuses at PRECHECK,
nothing changed, nothing of the host looked at. It is a change of the process, not of the host: it is not a mutating
call (mutate() is not used, and a later refusal is still REFUSED_NOTHING_CHANGED). Why it closes D9: prctl(2) says the
dumpable attribute "determines whether core dumps are produced for the calling process upon delivery of a signal whose
default behavior is to produce a core dump"; in the kernel, do_coredump() (fs/coredump.c; vfs_coredump() in newer
kernels) returns before it formats the core name from kernel.core_pattern when the process's memory is not dumpable,
so no pipe helper (the host's crash collector) is started and no core file is created. RLIMIT_CORE is not relied on.
The attribute stays 0 until the process ends (only an exec or a change of credentials resets it; the source does
neither).

10. OPEN DECISIONS (for the signatories; none is decided by these bytes beyond what they say)

  D1  The forms of the definition refused although compose would read them the same: "export NAME=VALUE" and a quoted
      VALUE. Refused here (DESIGN.md section 4). If the host's file uses one of them, the run refuses with
      ENV_TOKEN_DEFINITION_NOT_PLAIN or ENV_TOKEN_VALUE_GRAMMAR and nothing changes; accepting either is a new revision.
      The cost is availability: a host file with CRLF line ends, a quoted token or a comment after it refuses the GO.
  D2  The value floor of 16 characters (a guard against a short placeholder; a long one such as
      "your-massive-api-token-here" passes it). The provider's keys are 32 characters.
  D3  The withdrawal (section 3.7): this candidate removes the file it created after a later failure, by identity. It is
      a declared exception to rule 4 of the core (which allows only the temporary of a run to be removed), signed in the
      scope; README line 205 gives the removal of an abandoned token file to the owner. Asked of the co-auditor: accept
      the exception in writing, or choose the alternative (leave the file and say LEFT_UNVERIFIED always).
  D4  ENV_FILE_OWNER_UNEXPECTED: the environment file must be owned by root or by the owner of the deploy directory
      (CORE.md: the deploy tree and .env owned by uid 1000; the release's deploy pipeline rewrites .env as that user).
  D5  The source cannot show that the running containers hold the same value as the file (they read it at their last
      recreate); asking docker would put the value in an argv. The file is what the next recreate uses. Nothing before
      Monday's first claim shows the key is valid for the provider's websocket stream (a REST-only or expired key fails
      only after claim 1).
  D6  The departures, all covered by the owner's decision record (which names the clause "not through the environment"
      only) and each to be read in writing by the co-auditor and confirmed by the owner:
        (a) the token is placed by a program, not by the README's manual recipe;
        (b) the program reads the content of .env, and reads back the content of the token file it wrote, once each, in
            memory, where ORD:25 says only the authorized process of the supervisor reads the content and the readback
            reads metadata only (the receipt carries none of it);
        (c) the first sentence of README line 207 ("This unit does not use it") stops being true; an erratum of the
            README after the epoch.
      It meets the clause it names: the file is read; no environment of a process, no docker inspect or exec.
      The alternative to (b) for the token file: drop the byte comparison (same inode, metadata and size only); kept,
      because the brief asks for it and it is the only proof that the bytes on disk are the bytes meant.
  D7  WRITE_WEEKEND narrowed in the operation instead of a new date class in the core.
  D8  The proof workflow runs only this operation's proof (the earlier operations were proved on their own branches and
      only their seals are checked). The job uses the network once (apt-get install python3-pytest, as the core's
      run.sh does) and docker compose as the runner's user for the agreement stage (config only); no shape needs either.
  D9  CLOSED in revision 3 by a mechanism (3.10, section 13): the process is made non-dumpable before anything is
      opened, or the run refuses with nothing changed. The co-auditor did not accept the residual of revision 2c (a
      crash forwarding the whole .env through the host's pipe to its crash collector; RLIMIT_CORE=0 does not stop a
      pipe) and accepted a minimal revision of the core that imposes the protection before the read; this is that
      revision, to be reviewed by hash and bound anew. What it does not touch (DESIGN.md section 8): copies of the value
      in the memory of the process until it ends; swap, a kernel crash dump of the whole machine (kdump) and root's own
      access to the memory of a process are not core dumps of this process and are not changed by it.
  D10 The instant 2026-10-04T11:15:00Z (section 4) is a rule of the binding, not a refusal of the source: a window
      after it, and before Monday, would still place a token Monday's first claim can use, and only the owner decides
      such a run (with its own metadata readback before Monday).
  D11 Two definitions with different values are refused, even the template line "MASSIVE_API_TOKEN=" left above a
      filled one (compose keeps the last of a name; the backend the prefixed name first). Accepting it means deciding
      which definition the backend uses; it is a new revision if the host's file has that form.
