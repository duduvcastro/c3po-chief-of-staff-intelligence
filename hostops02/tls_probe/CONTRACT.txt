socket.massive.com:443 succeeds from @NETWORK@, without a token", for the network the owner's sheet chose for the unit
(FOLHA_SABADO_0900.rev5, item 7: bridge). One attached container of the signed image ID:
    docker run --rm -i --pull never --init --user 0:0 --network bridge --read-only --cap-drop ALL
      --security-opt no-new-privileges --log-driver none --name hostops02-tls-<first 16 hex of the GO sha256>
      <image ID> python -I -B -
with the fixed environment of the core (PATH=/usr/bin:/bin LANG=C LC_ALL=C, no HOME, no DOCKER_CONFIG), working
directory "/", standard error discarded, the pinned probe script (5914 bytes carried in the source) on standard input,
at most 20 seconds (class RUN_SHORT) and 65,536 bytes of output. It is the core's RUN_PREFIX (the README's catalog argv)
with one word changed, none -> bridge, one option added at its end, --log-driver none (the engine keeps no log of the
container's output, whatever the host's default log driver: json-file and local would remove it with the container,
journald and syslog would keep it on the host, gelf, fluentd, awslogs and splunk would ship it elsewhere; the attached
output still reaches the CLI), and --name. No bind, no --mount, no -e, no --env-file, no token, no file of

docker ps -a. After it: docker ps -a again. Five docker commands in three shapes, no other process, no shell, no
systemctl. Nothing on the filesystem of the host is created, changed or removed by this process.

The provider host and port come from the release code, not from a person: the transport opens
wss://socket.massive.com/stocks (c3po/backend/app/r2d2_v2_massive_transport.py line 99 at dd4ec4bb), with no port in
the URI, so the port is the wss default 443 (the websockets client that requirements.txt line 8 pins, websockets>=14,<16:
uri.py "443 if secure"); the README names the same pair at line 580. The transport's own client resolves the name,
connects with socket.create_connection and wraps the socket with ssl.create_default_context() and the server name
socket.massive.com (websockets sync/client.py, read in version 15.0.1): the probe does the same three steps with the
same trust store of the image, and nothing after them.

The probe script (PROBE_SCRIPT, sha256 8748e274..., read it in op.py): its first statement arms a 14 s alarm; it takes
ssl.create_default_context() and refuses to go on unless the context requires a certificate and checks the host name
(status TLS_CONTEXT_NOT_VERIFYING); resolves socket.massive.com:443 (every family) in a thread joined for at most 4 s
(DNS); counts the distinct IPv4 and IPv6 answers (at most 16); tries them in order within 4 s in total until one TCP
connection is established, as socket.create_connection does (TCP; an attempt whose socket cannot even be made, a
kernel without IPv6 for example, is TCP_UNREACHABLE and the next address is tried); makes ONE TLS handshake on that
connection with server name socket.massive.com, bounded by 4 s (TLS); on success takes the TLS version, the cipher name
and the SHA-256 of the leaf certificate's DER; closes the socket; prints ONE JSON line and ends with os._exit(0). It
calls no send, no write but the line on standard output, no read after the handshake, no unwrap (no close_notify), no
HTTP. Every outcome is a constant status and a constant code; no text of an exception, no address and no name of the
certificate leaves it.

What leaves the host, said in the signed effects (provider: dns, tcp_attempts_max 16, connections_established_max 1,
tls_handshakes_max 1) and in the owner's question: A and AAAA queries for socket.massive.com to the resolvers the
engine gives the network bridge (musl, the C library of the image, adds no search domain to a name with two dots
unless the resolver configuration sets ndots above 2); TCP connection attempts to port 443 of the addresses of the
answer, in order, at most 16 within 4 s, of which at most one is established; one TLS handshake on that connection.
Nothing else.

HTTP request: NONE, by decision. The README's item asks only for the TLS connection; the A1 row C3 says "sem token; nao
envia nada" and "abre uma conexao TLS com o provedor e fecha". An unauthenticated HTTP request would put application
bytes in the provider's logs and adds nothing to what the item asks (DNS, egress and CA trust from the network bridge,
README line 593): a GET to a WebSocket endpoint without the upgrade says nothing about the supervisor's own session,
and its first application frame carries the token, which this run must never have.

6. WHAT A RECEIPT MEANS FOR THE GATES

  KNOWN_COMPLETE, outcome TLS_VERIFIED_TO_THE_PROVIDER_HOST
      Rehearsal item 2 is closed for the network bridge, for the image in production, on this host, at that instant:
      the container resolved socket.massive.com, connected to port 443 and completed a TLS handshake whose certificate
      chain and host name the image's default trust store verified; it sent no application byte; the engine removed
      it. It is the condition of sheet line 9 for installing the units with @NETWORK@=bridge (E3). It says nothing
      about the provider's service, the token, the WebSocket upgrade, or the network at 05:2x on Monday.
  KNOWN_REFUSAL (exit 1)
      Nothing was started and nothing went to the network. The signature is spent. The A1 has no second band for C3:
      a new attempt is a new request with a new "Assino" inside what is left of the band, only if the A1 section 8
      allows it; otherwise sheet line 9 decides (waiver only by the owner).
  KNOWN_PARTIAL (exit 2): read outcome and code.
      PROBE_RAN_TLS_NOT_VERIFIED: the network of the unit is NOT proven; the code says which step failed. Do not install
      the units with bridge on the strength of this receipt: a decision of the owner (sheet line 9) and, for a fix of
      the network, a new rehearsal.
      TLS_VERIFIED_WITH_FINDINGS: the TLS path is proven (tls_verified true); the finding is about docker (a status, a
      listing, a container left). Whether E3 may follow is a written reading of the signatories after a read-only look
