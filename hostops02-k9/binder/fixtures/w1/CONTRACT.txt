Why the earlier read ended KNOWN_PARTIAL, and what is changed here
The read of 2026-10-02 reported three problems (containers:CONTAINER_CHANGED, containers:FAMILY_ROW_INCOMPLETE,
data_volume:FAMILY_MOUNT_FACTS_INCOMPLETE). All three have one cause. The payload compared two raw inspect
answers of each container; the Docker daemon builds the Mounts list by ranging over a map, so two answers for an
unchanged container list the same mounts in different orders. The second and third problems are roll-ups of the
first. No container had changed. Here both lists that the template ranges over (mounts, networks) are put in
canonical order before the two answers are compared, and a row that still differs names the keys that changed
(changed_keys). A real restart between the two reads is still CONTAINER_CHANGED. The receipt of that run keeps
only the first answer of each row, so this cause is an inference, not a recorded diff; the emulated daemon of the
test file now returns Mounts in another order on every call and reproduces it. The families that needed fixes in
the earlier revision are not repeated here: no entry name is listed (lost+found), docker-init is not probed again
and docker info is not run.
Three more causes of a PARTIAL that this host would have produced with the new families are removed by design:
no entry name is emitted at all (so no name can be "withheld"); the pending-reboot flag is read at /run, not
through the link at /var/run; something that is legitimately absent before provisioning is a fact.

What the fixed tools and this process do besides reading (SCOPE side_effects: part of the signed request, to be
named in the GO)
  1. Starting the daemon. With the standard packaging the Docker daemon is started on demand through docker.socket:
     a client call to the endpoint of a STOPPED daemon makes systemd start docker.service, and the started daemon
     restarts every container that has a restart policy. Therefore no docker command, and not even the lookup of
     the docker binary, happens before systemctl show answered ActiveState=active for docker.service in this run.
     Not covered: a daemon that stops between that answer and a later docker command. Whether docker.socket is
     enabled on this host was not measured; the rule does not depend on it.
  2. Every docker command names the endpoint unix:///var/run/docker.sock in its argv (--host), so that a client
     context in root's configuration cannot send a read to another endpoint. The Docker CLI still loads its
     client configuration file from root's home directory when one exists; its content never reaches the payload.
  3. Every inspect: the Docker CLI receives the whole inspect document from the daemon, environment and addresses
     included, to render the template. The payload receives the template output only. Not new on this host.
  4. systemctl show of a unit that is not loaded makes the manager look for its unit file. Nothing is started.
  5. pgrep reads the command line of every process. The payload receives one number per pattern.
  6. Signals: a child that exceeds its time limit is sent SIGKILL by this process. No other signal is sent.
  7. Each child gets the null device as stdin and stderr; the Python library opens it read-write. Nothing is
     written to it.
  8. Access times: every open of this process outside /proc carries O_NOATIME (a test asserts it on every open).
     readlink of /var/run and the file reads of the three tools themselves may move access times under the mount
     options of the host.
  9. Automounts: nothing is opened at or below a mount point whose last mount table row is autofs, and no tree is
     descended that has such a point below it (AUTOMOUNT_PATH_REFUSED, a problem). The table is read from /proc
     before that check exists; without a mount table the check is not applied and automount_guard says so. The
     receipt reports the number of autofs rows and of armed points.
  docker info (CLI plugin round as root), timedatectl (may start a service) and getent (name-service lookup) are
  NOT run by this operation.

DECISIONS THAT NEED THE REVIEWER'S AND THE OWNER'S EXPLICIT ACCEPTANCE
1. Nine UTC dates, one set of bytes for several reads. These bytes are meant to serve the first preflight and
   the later reads that the plan gives to the same source, through Saturday 10/10. The source and the dispatcher
   accept a window that lies entirely on ONE UTC date of 2026-10-02, 2026-10-03, 2026-10-04, 2026-10-05,
   2026-10-06, 2026-10-07, 2026-10-08, 2026-10-09 or 2026-10-10 (never across midnight UTC; 21:00 BRT is 00:00
   UTC), and the request must name exactly this set, in this order. Each read is a binding of its own: request,
   authority, GO, window and signatures, single-use; no GO serves two reads, and a wider date set does not widen
   any window. The reviewed dispatcher accepted one literal date; this is the one line of it whose logic changes
   (== becomes "in (nine literals)"). Revision 2 accepted two dates. Alternative: a shorter set, and a rebuilt
   candidate when a read falls outside it.
2. Candidates in the signed request. The release directory name for this epoch and the capacity tree path are not
   decided. They are NOT constants of the source: request.collection.candidates carries at most 4 release
   directory names (one path component each, [A-Za-z0-9._=-]{1,64}) and at most 3 absolute clean paths, validated
   before any claim and before any observation. Both lists are empty in the template, and W1 runs with empty
   lists (the two families then read nothing and say so as a finding). The binding step may fill them; the owner
   signs the request either way. The names are never copied into the receipt: it refers to candidate_index.
3. launcher_stdin.py is the reviewed file, byte for byte. Its three family literals still say "hostfacts": the
   module name under which the source is executed, the file name in tracebacks that are never printed, and the
   schema field of a REFUSAL document (READONLY_SUPERVISOR_HOSTFACTS_STDIN_RESULT_V1). Nothing validates that
   field; a refusal is bound to this operation by exit.json (config, request and GO hashes), and the dispatcher
   rebuilds the final payload from this source and these documents and demands byte equality, so no payload of
   the earlier operation can be sent. Consequence to accept: the stdout of a refused W1 run is byte for byte the
   stdout of a refused run of the earlier operation; it is told apart by exit.json ONLY, and the scope sentence
   of the GO must say so. Alternative: a 3-line delta that renames the label, and a new launcher hash.
4. Three templates never run on any engine (ENVFLAGS_FORMAT, ATTACH_FORMAT, NETWORK_FORMAT). Each is in its own
   call and its failure costs one problem in one section (worker_environment or network), with every other fact
   intact. The five templates of the earlier read are reused byte for byte.
5. A third binary, pgrep. It is the only way to learn of a stray V2 process without command lines entering the
   payload. If it is unwanted, drop the section: one table entry and one function.
6. File contents. This operation reads the content of nine files (SCOPE file_contents_read): this process's
   mountinfo, /proc/sys/kernel/osrelease, .deploy-version, the controller policy, two controller reports and
   three controller modules (hashed only). The earlier read opened only two /proc map files. The reports hold
   package and container names; none is emitted. The package list, the reboot state file and the release files
   are deliberately NOT opened.
7. The data source is not walked unless it is one of two signed paths (/mnt/day-d-data, or the docker volume path
   of c3po_c3po_day_d_data). The earlier read walked whatever path the mount named.
8. When no running container shows the data mount (docker down, or rows unreadable) the signed default
   /mnt/day-d-data is still read and the receipt says source_basis SIGNED_DEFAULT_NO_CARRIER; the section is
   PARTIAL in that case, unless every container was read and none mounts it (then it is the finding
   DATA_MOUNT_NOT_FOUND).
9. Access time. Directories are opened O_NOATIME and the access time is compared before and after. A change is a
   problem on quiet directories (volume root, configuration directories, capacity tree) and a fact on directories
   that running services write and poll (raw spool, source directory, release directory, journal root).
10. All listed containers are classified, running or not (the earlier read classified the running ones), so that
   a stopped second worker or a leftover one-off container is counted. The data source, however, is taken from
   the running containers that are not one-off only.
11. docker.service must be seen active before any docker command (side effect 1). If systemctl cannot answer, or
   answers anything but active, every docker family is a problem and the run is PARTIAL: the price of never
   starting a stopped daemon.
12. A new argv form: every docker command begins with --host unix:///var/run/docker.sock, the Docker CLI's own
   default endpoint written out. The earlier reads relied on the default; this exact form was never run on this
   host. Alternative: drop the two arguments and accept that a client context could redirect the reads.
13. Two shared budgets. The docker families share 25 s (limit docker_seconds); a daemon that answers slowly
   without timing out loses the rest of its own families, never the others. systemctl and pgrep share 15 s in
   the same way (limit system_tools_seconds, new in revision 3): slow answers there cost the unit states and the

Limits
Budget as in the reviewed dispatcher: watchdog 80 s, remote collection 60 s, latest_start = not_after - 80 s.
Each command: fixed argv from the signed table, absolute binary chosen after an lstat safety walk, no shell, env
exactly PATH=/usr/bin:/bin LANG=C LC_ALL=C, stdin and stderr /dev/null, output capped at 64 KiB, 5 s timeout (the
earlier read used 8 s), a tool is skipped after its second timeout. Two budgets bound what the tools can use
whether they hang or only answer slowly: systemctl and pgrep share 15 s, the docker commands share 25 s. Each
budget runs from the first command of its group, and a command of a group is started only while the group has
used less than its budget; a group therefore ends at most one command after its budget, and one command lasts
at most 5 s (up to 1 s more when the child has to be killed and waited for). Worst case, by timeouts, by slow
answers or by both: 15 s + 5 s for systemctl and pgrep, then 25 s + 5 s for the docker families: 50 s (52 s
with the two kill waits), and the data volume is read in what is left of the 60 s. When every command hangs:
systemctl is skipped after two timeouts and the next timeout, of pgrep, ends the shared budget: 15 s; docker
two timeouts: 10 s. The one optional argument of a command is a 64-hex container id, a sha256 image id or a
signed tag, checked before the call. Expected: 53 commands on the emulated post-deploy stack (38 docker, 11
systemctl, 4 pgrep).
KNOWN LIMIT, family-wide: the deadlines are cooperative. A subprocess is bounded and killed, but open, scandir,
lstat or fstatvfs on a hung filesystem would block past the budget; the local watchdog would then kill only the
SSH client. All paths are expected on local block devices, tmpfs or procfs; a path that an armed automount point
of the mount table holds is refused before it is opened (side effect 9).
Directories: at most 20000 entries are counted per directory (one lstat each); beyond that the count is capped and
flagged. It is a problem (CENSUS_CAPPED) at the volume root, at the journal root and in the reader-input trees,
and a flag only in the configuration directories and capacity roots, whose aggregates then describe the first
20000 entries. The reader's own limit is 4096 files.
Receipt: JSON, sorted keys, compact. The dispatcher decodes at most 65536 bytes. The payload seals at most 60000
bytes by four explicit reductions applied in order and listed in observation.size_reductions (histograms dropped,
mounts dropped, container rows reduced, sections reduced), each forcing PARTIAL; the final assembly cannot
raise. Measured on the emulated host (VALIDATION.json): about 35 kB before provisioning and about 41 kB after
provisioning with both candidates signed, no reduction.
