6. WHAT A RECEIPT MEANS FOR THE GATES

  M2p (Sunday, PRE FULL). KNOWN_COMPLETE with the outcome EPOCH_DRY_RUN_PRE_ALL_OBSERVED_ALL_EXPECTATIONS_MET (receipt
  member dry_run FULL, effects member rehearses_install_release_and_activate true) means, for the instant of the run
  and this boot: the release bytes that M1 will install are accepted by the deployed code in the deployed image with
  the revision the worker runs; the policy bytes M3 will deliver are canonical and accepted by both validators at
  every signed instant; a read-only bind of a private directory is readable by the worker's reader; nothing stands
  where M1 and M3 will create, their parents are the signed directories with rows those writes accept, and their
  filesystems have the signed free bytes and inodes; no container is left by an interrupted recreate of the worker;
  the override M3 will write, in M3's bytes, renders to exactly the four intended
  values, changes nothing else and leaves both files reachable through the one signed read-write bind; the running
  worker carries none of the four names; docker answered within the signed milliseconds; image, worker and deployed
  revision are as signed; the pin is there and is root's; the lock file exists; no reboot is pending.
  It does NOT mean that M1, M2 or M3 will complete: it is a read on another day, and it says nothing of a host that
  was changed after it (a second full PRE follows any such change). It is never the readback of ORD:7.
  A PRE REDUCED receipt, whatever its outcome, is a diagnosis and nothing M1 or M3 may stand on.
  A finding on Sunday is a state of the host to correct, or a parameter to correct, before Monday; a failed
  observation is a shape to look at with the receipt in hand (the item says which command, with which constant code
  and after how many milliseconds).
  When the container ended with docker's own status 125, 126 or 127 (VERIFY_ENGINE_FAILURE) the receipt carries the
  status only: the frozen runner discards standard error. What the same receipt still tells: the image item says
  whether the signed reference resolves to the signed ID (an image that is not present by that ID is 125); the
  containers item says whether a container of this run's name is listed (a name in use is 125; it is derived from the
  single-use GO, so only a leftover of this very run can hold it); items.verify.binds says whether a bind was asked
  for (0 in a reduced PRE without probe: then the cause is not the mount); directory:BIND_PROBE or release_target
  says whether the bind source was the signed directory. 126 and 127: the command could not be started in the
  container (python not found by that name, or not executable). What is left after that elimination is the engine
  itself (the init binary, the daemon).

  M2 (Monday, POST). KNOWN_COMPLETE with the POST outcome (receipt member gates_first_session_readback true) is the
  readback of the first session: the installed file is the signed release byte for byte, private as the worker's
  reader requires, verified by the deployed code through the bind, and the policy candidate is accepted. M3 does not
  depend on this receipt by hash (its request was signed before): it reads the installed release again by itself.
  M3 IS DISPATCHED ONLY WITH THIS RECEIPT IN HAND: it carries items.containers.verify_container_present false, and
  activate refuses nothing but ends PARTIAL after the recreate if a container it listed disappears under it.
  KNOWN_PARTIAL: the readback is not complete. Which it is, a finding (OBSERVED_ALL_EXPECTATIONS_NOT_MET: the host is
  not as signed) or an observation that failed (PARTIAL_OBSERVED: the run could not see), is in outcome and code; the
  signed order decides what follows, not this source. KNOWN_REFUSAL: nothing was looked at; the GO is spent.
  UNCERTAIN: nothing can be said; the source changed nothing on the filesystem in any case, and a container of this
  run, if one is left, is named hostops02-k11-<first 16 hex of the GO hash>: one read that shows no container of
  that name comes before M3.
  The residual the signers of M2 accept in writing: these items gate and cannot be left out of a POST request, so an
  observation of any of them that fails (a docker read that times out, a listing the source cannot parse) makes M2
  KNOWN_PARTIAL though nothing is wrong with the release: boot, the three directories, release_target, verify,
  containers, image, worker, deploy_files, maintenance_pin, reboot_pending, directories_stable. Items that are facts
  only (reboot_required, units without expectation, the journal without a floor) no longer do.

  What the signers choose by the plan is what gates: an omitted item gates nothing and the receipt lists it.

      BUILD_EQUAL; shasum -a 256 -c CORE_SHA256SUMS in the core. The dispatcher refuses the template as it is.
   2. Receipts on record, each with its hash; every row copied from a receipt named in evidence, of the boot named by
      evidence_boot_id_sha256.
   3. Fill the plan (section 7). Compute every hash and size by command. Write every instant with isoformat().
      PRE: content_b64 of the release; POST: null. Check by command that the override bytes are K6a's override_of for
      K6a's request, that release.parent rows are byte-equal to K10's and live.parent rows to K6a's live_parent.

      the three sibling payload hashes they ran against next to the request (SIBLINGS.txt is that record for the seal).
   4. request: status BOUND, date, windows, host binding, executor_uid 0, evidence; canonical bytes; hash. The bound
      request must stay below 65536 bytes (the plan refuses a release above 24576 bytes).
   5. effects: compute once with the source's effects_of(plan) offline and READ it: it is what the owner and the GO
      sign. authority and GO carry it literally.
   6. authority (owner, SIGNED, APPROVED, request and payload hashes) -> hash -> GO (SIGNED, GO, three hashes,
      transport_binding with the four runtime pins and the command pin, claim_root_identity, the constant
      scope_statement, success_criterion = success_of(plan): the outcome of the signed mode).
   7. Six instants non-null, on request.date, gate span at most 3600 s; config window inside both;
      latest_start = not_after - 80 s. Avoid HH:05-07, HH:10-25 and HH:35-37 (the lock probe and the engine).
   8. Final payload with launcher_stdin.build; config with its pins and the paths of the five bound blobs;
      publication proof.
   9. Dry validation: the source's authenticate() on the bound bytes with the target uid injected, and perform() with
      a gate that raises - nothing may be touched (tests: a host object that fails on any use).
  10. Publish the hashes of the final payload and of the config. Prepare -> publication -> resume, once.
  11. Order. The full PRE is dispatched as soon as the release, the policy and the reviewed K10 and K6a bytes exist,
